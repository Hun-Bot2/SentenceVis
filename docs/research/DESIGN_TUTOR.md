# SentenScope 설계 탐구 노트

**상태:** `[PLAN]` 학습 자료, 2026-11-13. **설계 답안과 사용자 결정란은 비워 둔다.** 기존 명세는 비교할 후보이며, 이 문서가 후보를 승인하지 않는다. 사실과 공식·수학 정의는 설명할 수 있지만, “그러므로 이 프로젝트에는 X를 쓰자”라는 결론은 사용자가 작성한다.

## 사용 방법

각 회차에 한 질문만 다룬다. 먼저 첫 힌트로 생각을 기록하고, 필요할 때만 접힌 다음 힌트를 연다. 대화에서는 다음 힌트를 미리 모두 설명하지 않는다. 에이전트는 반례·출처 확인을 돕되 사용자의 이유 문장을 대신 완성하지 않는다.

읽기 순서는 선택할 수 있다. 출발 질문: **이 화면을 본 사람이 어떤 판단을 할 수 있어야 하는가?** 아직 차트 이름이나 색 이름을 쓰지 않고 한 문장으로 적어본다. 참고자료 F#는 [RESEARCH_REFERENCES.md](RESEARCH_REFERENCES.md)에 원문과 확인 범위가 있다.

## H1. 왜 이 속성을 x축에 놓을까?

**첫 힌트 — 관찰:** T1에서 ‘양쪽 값을 읽기’, ‘큰 차이 찾기’, ‘특정 피고인 찾기’는 같은 읽기 동작일까? 먼저 하나를 골라 필요한 데이터 항목만 적어본다. [F1, F2]

<details><summary>다음 힌트 — 읽을 개념</summary>

정량/범주/순서와 위치·길이·면적의 구별을 참고해본다. 공통 척도의 위치에 관한 지각 연구와 가로/세로 방향의 선택은 동일한 주장인지 점검해본다. 연구의 실험 과제가 자신이 적은 동작과 어디까지 같은지 표시한다.
</details>

<details><summary>다음 힌트 — 작은 비교와 계산</summary>

같은 가상 수치를 가로 배치와 세로 배치로 그려보고, 라벨 길이와 읽기 동작만 비교해본다. 이것은 데이터 finding이 아닌 스케치 연습이다.

선형 좌표변환의 정의는 다음과 같다. [F7]

```text
p(v) = p0 + (v-a)/(b-a) × (p1-p0),  a ≠ b
```

`[a,b]`는 데이터 범위, `[p0,p1]`은 픽셀 범위다. 수식을 사용해 domain을 바꾸었을 때 같은 값 차이가 차지하는 화면 거리를 직접 계산해본다. 축의 방향, 원점, 잘린 범위, 이상치 처리 중 무엇을 이 식만으로 정할 수 있고 무엇은 별도 판단이 필요한지 나눠본다.
</details>

## H2. 왜 이 도형·채움·면적을 사용할까?

**첫 힌트 — 관찰:** 도형으로 구별하려는 것이 주체, 심급, 검증 상태 중 무엇인지 하나씩 써본다. 범주의 수와 순서가 있는지도 적는다. [F2, F4]

<details><summary>다음 힌트 — 그룹화와 기호</summary>

유사성·근접성·연결에 관한 Gestalt 리뷰를 참고해본다. 같은 도형이지만 멀리 있는 요소와 다른 도형이지만 붙어 있는 요소가 있을 때 무엇을 먼저 묶어 읽는지 스케치에서 관찰해본다. 연결선 자체가 데이터에 없는 관계를 암시하는지도 살펴본다.
</details>

<details><summary>다음 힌트 — 크기와 겹침</summary>

면적 `A`를 원으로 표현한다면 `r = sqrt(A/π)`다. 반지름을 값에 비례시키는 경우와 면적을 값에 비례시키는 경우를 계산해본다. 수량을 표현하지 않는 범주 기호라면 이 계산이 필요한지도 먼저 검토한다. 비어 있는 점과 채운 점이 같은 좌표에 놓일 때, 작은 화면에서 기호의 무엇을 읽을 수 있는지 확인한다. 수식은 기하 정의이며 도형 선택의 정답이 아니다.
</details>

## H3. 왜 이 색인가? — 구별·순서·의미 연상을 따로 보기

**첫 힌트 — 관찰:** 범례 없이 색 견본을 보았을 때 떠오르는 단어를 먼저 적어본다. 이어 범례를 붙였을 때 달라지는 해석을 적는다. 빨강/초록을 포함해도 좋지만 색 이름으로 선택을 확정하지 않는다. [F3]

<details><summary>다음 힌트 — 세 개의 독립 질문</summary>

ColorBrewer의 qualitative/sequential/diverging 설명을 참고해본다. 동시에 Lin et al.의 색–개념 연상 실험을 읽어본다. ‘서로 보이는가’, ‘순서가 읽히는가’, ‘사회적·개인적 의미가 떠오르는가’를 별도 열로 작성해본다. 한 문화·과제의 관찰을 모든 사람에게 일반화할 수 있는지 출처 범위를 점검한다.
</details>

<details><summary>다음 힌트 — 검출을 계산하기</summary>

WCAG의 대비 정의를 참고해본다. [F6]

```text
CR = (L밝음 + 0.05) / (L어두움 + 0.05)
L = 0.2126R + 0.7152G + 0.0722B
```

여기서 R/G/B는 8비트 값을 그대로 넣는 것이 아니라 선형화한 sRGB 성분이다. 각 성분 `c`를 0–1로 정규화한 뒤 `c ≤ 0.04045`이면 `c/12.92`, 아니면 `((c+0.055)/1.055)^2.4`를 사용한다. 표준의 정의와 적용 대상·예외를 함께 확인한다. 대비 기준을 통과한 두 색이 의미상 적절한지는 별도의 질문으로 남긴다.

실제 배경색 위의 텍스트·선·선택 상태를 계산하고, 색을 제거한 스케치도 비교해본다. 계산값과 실제 화면의 얇은 선 가독성은 따로 기록한다.
</details>

## H4. 왜 노드와 연결선인가? 왜 이런 배치인가?

**첫 힌트 — 관찰:** 간선 하나를 자연어로 읽어본다. ‘대응’, ‘문서 내 순서’, ‘참조’, ‘법원이 명시한 관계’ 중 실제 데이터가 지지하는 것은 무엇일까? 서로 다른 의미의 간선을 같은 것으로 취급하고 있지는 않은지 살펴본다. [F4, F7, F8]

<details><summary>다음 힌트 — 대안과 공간 의미</summary>

같은 작은 관계 집합을 표·계층 배치·자유 배치로 옮겨본다. 노드 간 거리나 좌우 순서가 사용자에게 어떤 뜻으로 읽힐지 각각 적어본다. D3 force의 물리적 시뮬레이션과 dot의 계층 배치 설명을 비교해서 읽어본다. Graphviz는 읽기 자료이며 과제 렌더러 변경 요청이 아니다.
</details>

<details><summary>다음 힌트 — 레이아웃 품질을 수량화하기</summary>

아래는 **탐구용 목적함수 초안**이다. 특정 논문의 공인 품질 점수나 D3 force의 내부 목적함수가 아니다.

```text
J = λc C + λo O + λl L + λs S
C: 공유 끝점을 제외한 간선 교차 수
O: 겹치는 라벨 사각형의 면적 합
L: 간선 길이 합 / (간선 수 × 화면 대각선 길이)
S: 동일 노드의 이전 화면 대비 이동거리 합 / (노드 수 × 화면 대각선 길이)
```

λ는 사용자 판단 전이며 값을 제안하지 않는다. 빈 그래프 등 분모가 0이면 지표는 미정의로 기록한다. 각 항의 척도·정규화가 다른데 그대로 더하면 무슨 일이 생길지 살펴본다. 교차를 줄인 배치가 라벨 읽기와 선택 후 위치 기억에도 유리한지 별도로 비교해본다. 방향·레이블 가시성 같은 조건을 비용 항과 제약 조건 중 어디에 둘지도 기록한다. 그리기 위한 라우팅 점과 실제 근거 노드를 구별한다.
</details>

<details><summary>다음 힌트 — 사용자 의도 분류</summary>

</details>

<details><summary>다음 힌트 — 동작을 재현하기</summary>

</details>

## H6. 왜 이 범례·검증 표시인가?

**첫 힌트 — 관찰:** 데이터의 출처, 사람이 확인한 상태, 모델 점수가 각각 어떤 질문에 답하는지 적어본다. 한 줄의 좋음/나쁨 순서로 놓을 수 있는지 검토한다. [F6, F8]

<details><summary>다음 힌트 — 읽기 자료와 조합</summary>

기존 R7의 동적 범례 논의와 Guo et al.의 calibration 정의를 참고해본다. `explicit_text + unreviewed`, `llm_extracted + reviewed`, `conflicted`, 원문 접근 불가를 각각 종이에 표시해본다. 표시는 아직 후보이며 기호·색을 확정하지 않는다. 사람 검토 완료가 무엇을 확인했는지 설명 없이 얼마나 알 수 있는지도 점검한다.
</details>

<details><summary>다음 힌트 — 해독과 검증의 분리</summary>

범례를 보고 ‘이 기호는 무엇인가’를 답하는 일과, 실제 원문을 찾아 ‘이 관계는 근거가 있는가’를 답하는 일을 따로 해본다. 두 과제에서 다른 오류가 나올 때 어떤 관측을 남겨야 할지 적는다. 검토 완료 수와 실제로 일치한다고 판정한 수의 분모도 따로 기록한다.
</details>

## H7. 왜 ML/DL이 필요한가? 무엇을 맞혀야 하는가?

**첫 힌트 — 관찰:** 사건 연결·사람 대응·문장 추출·관계 분류·설명 생성 중 자동화하려는 작업을 하나만 적는다. 입력과 출력, 오답일 때 화면에 생기는 변화를 써본다. AI 도입 자체는 과제 목적이나 검증 결과가 아니다. [F8]

<details><summary>다음 힌트 — 기준선과 정답 단위</summary>

규칙 기반 추출, 사람이 검토한 구조화, 모델 추출을 같은 문서에서 비교하려면 무엇을 같게 해야 할지 적어본다. LegalViz의 그래프 구조·텍스트·법률 내용 평가 구분을 참고해본다. 동일 사건의 다른 심급·공동피고인·중복 문서가 학습/평가에 나뉠 때 정답 정보가 새어 나가는지 검사한다. 모델·분할 단위는 아직 선택하지 않는다.
</details>

<details><summary>다음 힌트 — 지표의 정의</summary>

```text
precision = TP/(TP+FP)
recall    = TP/(TP+FN)
F1        = 2TP/(2TP+FP+FN)
```

이는 이진 판정의 정의다. 분모가 0인 경우 보고 방식을 명시한다. 다중 라벨·범주 평균은 별도 정의가 필요하다. [F8]

TP 하나가 ‘단어’, ‘정확한 span’, ‘같은 피고인의 관계’, ‘양쪽 근거가 맞는 경로’ 중 무엇인지 먼저 정해본다. 낮은 빈도의 직권 쟁점 오류가 전체 평균에서 어떻게 보일지 작은 가상 혼동행렬로 계산해본다. 보류 비율·유효 출력 범위와 정확도를 함께 적어본다. 숫자를 실제 추출 성능으로 보고하지 않는다. 모델의 자기보고 확신과 정답 빈도의 차이는 calibration 자료를 참고한다.
</details>

## H8. 왜 이 평가라야 설계 이유를 검토할 수 있을까?

**첫 힌트 — 관찰:** 자신이 쓴 이유에서 ‘더 잘’, ‘쉽게’, ‘빠르게’를 찾아 밑줄을 긋는다. 그 말을 관측하려면 무엇을 기록해야 할지 하나씩 적는다. [F1, F2, F5]

<details><summary>다음 힌트 — 같은 정보와 다른 표현</summary>

동일 데이터·근거·용어 해설을 제공하는 표/문서와 자신의 후보를 나란히 놓아본다. 차이가 데이터 추가인지 표현/상호작용인지 구분한다. 아직 `TASK.md`의 비교 실험을 수행했다는 뜻이 아니다. 정식 참가자 연구는 기존 연구윤리 계획을 따른다.
</details>

<details><summary>다음 힌트 — 반증 조건</summary>

자신의 선택이 실패했다고 인정할 관찰을 하나 적는다. 가독성·정확도·시간·출처 오인·과밀도 중 무엇을 측정할지 선택해본다. 5초, 채널 2–3개, 표본 20–30개 같은 기존 문서 숫자가 문헌의 법칙인지 내부 목표인지도 구별해본다.
</details>
