# EVALUATION — Case Study, Findings, Usability, Validity

> **2026-11-13 검토:** 구체적인 축·도형·색·뷰 배치·인터랙션은 기존 제안 후보이며 사용자 결정 전이다. 아래 선택 문구는 확정/승인 기록이 아니다. 선택 이유를 에이전트가 대신 결론내리지 않는다. [단계별 힌트](../research/DESIGN_TUTOR.md) · [근거와 확인 범위](../research/RESEARCH_REFERENCES.md) · [검토 기록](../records/REVIEW.md).

**상태:** 평가 계획 [ASSIGNMENT + PLAN]. 실제 발견·평가 결과·참여자 수는 아직 없음.
**과제의 필수:** Primary Persona가 시각화로 T1–T3을 수행하여 얻은 **서로 다른 실제 findings 3개 이상 + 화면 스크린샷**.

## 1. 평가 목표

1. **Effectiveness:** 실제 형량/집행유예 변화를 탐지하고 두 판결문 근거에 연결되는가?
2. **Interpretability:** `배척`과 `직권판단`, `법령의 적용`과 `단순 언급`을 혼동하지 않는가?
3. **Usability:** 복잡한 항소이유에서 보고 싶은 경로와 출처 문장을 적은 클릭으로 찾는가?
4. **Robustness:** 모호하거나 검증 전인 연결을 사실로 오인하지 않게 하는가?

위 항목은 **평가할 질문**이며 결과가 아니다.

## 2. 필수 Case Study 설계

**주요 인물:** 김민지(Primary Persona), 비법률 전공 일반인.
**순서:** T1 Find → T2 Compare → T3 Verify.
**실제 finding은 직접 검증한 판결에서만 작성.** 데이터가 부족하면 연구 질문/표본을 줄이고 검증 가능한 범위만 제시.

### Candidate story A — 직권 법리오해로 변경된 사례 [PROPOSAL; 검증 필요]

- 탐색 단서: 제안서의 `2005고합52 → 2006노444`.
- *가설*: 제안서에는 징역 5년→3년 6개월, 피고인 주장 배척·직권 법리오해 관련 설명이 있음.
- 검증: 두 문서 사건쌍/피고인/주문, 항소이유별 결과, 직권 판단 구절, 실제 조문 적용을 수동 확인.
- 스크린샷: V1 행 선택, V2 직권 경로 선택, V3 근거 문장 비교.
- **주의:** “당사자 주장은 모두 기각됐는데 18개월이 자동으로 감형된 원인이 증명됐다” 식의 인과·절차 오독 금지.

### Candidate story B — 형기는 같지만 집행유예가 달라진 사례 [PROPOSAL; 검증 필요]

- 제안서에는 `8/37 unchanged-term candidates` 관련 메모가 있음. 실제 사례 ID는 따로 확정.
- 검증: 양쪽 주문에서 형기와 집행유예 유무를 정확히 대조.
- Finding 목표: 형기만 시각화하면 놓칠 수 있는 절차/집행 상태의 변화를 보여준다.
- 스크린샷: V1 기간 동일·집행유예 변경 표시, 범례, 근거 구절.

### Candidate story C — 서로 다른 항소이유 처리 혹은 조문 적용 변화 [PLAN; 사례 미선정]

- 예: 사실오인 배척, 양형부당 판단하지 않음, 원심 법령 적용 변경 등 **실제 확인된 패턴** 중 선택.
- 검증: `ground_type`, `disposition`, `statute_role` 모두 원문 대조.
- Finding 목표: 다양한 주장 처리 결과를 ‘감형 이유’라는 단일 라벨로 환원하지 않고 읽는다.
- 스크린샷: V2 상세 + V3 대응 원문.

> 위 세 항목은 **Case Study 후보/테스트 시나리오**이며 보고서에 쓸 수 있는 실제 연구 finding이 아니다. 확인 전에는 ‘발견했다’고 쓰지 않는다.

## 4. 선택 평가 — 간단한 형성적 사용성 테스트

필수 평가를 끝낸 후 **가능하면** 비법률 전공자 소규모(예: 4–6명) 대상으로 수행한다. 참여자 수는 현재 제안된 수치이며 확보 완료 인원이 아니다.

| 테스트 | 성공 조건 | 기록 |
|---|---|---|
| A. 징역/집행유예 차이 찾기 | 수치와 집행 상태를 올바르게 설명 | 성공/실패·시간·클릭 |
| B. 배척과 직권판단 구별 | `배척됐는데 판결 변경` 경로를 정확하게 설명 | 오류 유형·정정 후 변화 |
| C. 원문 위치 찾기 | 해당 1심·항소심 문장을 찾아줌 | 성공/실패·재탐색·범례 사용 |
| D. 범례 확인 | 색/도형/점선의 기본 의미 설명 | 혼동된 채널·설명 소요 |

- 태스크 순서는 참가자마다 바꾸는 것을 검토.
- **전/후 비교나 통계적 유의성**을 주장할 실험 설계가 아니라면 **형성적 관찰**로 기술.
- 참여자와 데이터 취급(녹화/로그 포함)은 동의를 얻고 과도한 개인 정보 수집 금지.
- 모집이 불가능하면 사용자 연구 효과를 주장하지 않고 전문가/자기평가, 테스트 로그와 한계를 명시.

## 5. 디자인 가설과 확인 방법

| 디자인 가설 | 테스트 | 결과 기록 |
|---|---|---|
| 공통축 위치가 형기 비교를 돕는다 | V1 변화량 질문 | 정확/오답, 사용한 단서 |
| 직권 판단을 별도 경로로 그리면 혼동이 줄어든다 | V2 ‘누가 제기했나’ 질문 | 직권/인용 오인 수 |
| 선택 경로만 원문을 펼치면 증거 검증이 쉽다 | V3 문장 찾기 | 찾기 성공/시간 |
| 전역 범례가 시각적 문법 이해를 돕는다 | 범례 노출/정의 확인 | 의미 해석의 일치/불일치 |

어떤 가설도 **사전에 참이라고 선언하지 않으며**, 사용성 테스트를 하지 못하면 논문 근거에 따른 디자인 *동기*로만 남긴다.

## 6. 연구적 위협과 정직한 기술

- **Construct validity:** `reasoning_change` 주석이 실제 법률적 논거를 온전히 나타내는가?
- **Internal validity:** 두 심급의 문장 대응을 원인-결과라고 잘못 추정하지 않았는가?
- **External validity:** 2002–2011년 일부 판결/비전문가 소수 사례를 전체 시민에게 일반화하지 않는가?
- **Data quality:** 공동피고인 정렬 오류와 검증 전 추출을 별도 집계했는가?
- **Implementation:** 원문 공개 제한 등으로 V3에 빈 구절이 나타날 때의 동작을 명시했는가?
