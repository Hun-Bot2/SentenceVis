## 3. 주 데이터 12: 원천과 라벨을 두 번 세지 않기

| subset | Training 원천 | Validation 원천 | 원천 표현 합계 | 라벨 표현 합계 |
|---|---:|---:|---:|---:|
| 일반판결 | 12,000 | 1,500 | 13,500 | 13,500 |
| 1–2–최종심 | 4,800 | 600 | 5,400 | 5,400 |
| 합계 | 16,800 | 2,100 | 18,900 | 18,900 |

심급 ZIP의 내부 묶음 디렉터리는 Training 1,600개 + Validation 200개 = **1,800개**다. **1,800개 묶음과 5,400개 문서는 다른 단위**다. 라벨의 심급 subset은 민사 3,788·가사 32·세무 283·일반행정 1,297문서로, 현재 라벨 분류상 형사 문서는 없다. 이를 모든 분류의 법률적 재판 종류를 독립 검증한 것으로 읽지 않는다.

### 원천 JSON: `PrecService`

대표 필드: `판례정보일련번호`, `사건번호`, `선고일자`, `법원명`, `사건종류명`, `사건명`, `판례내용`, `참조조문`, `참조판례` 등. 원천에 다른 구조의 행정심판례도 섞여 있다. 685개에는 일반 판결의 `사건종류명` 키가 없고 `행정심판례일련번호`·`재결청`·`의결일자` 같은 대체 메타데이터가 관측된다. 없던 사건종류를 생성하지 않았다.

### 라벨 JSON: `info + sections + annotations`

| 경로 | 관측한 구조 / 조사 시 의미 |
|---|---|
| `info.caseNoID` | 공급자 문서 식별값. 이것만으로 고유 키를 삼지 않음 |
| `info.caseNo/courtNm/judmnAdjuDe` | 사건번호·법원·날짜의 **라벨 원천값** |
| `info.caseClass` | 공급자 분류. 원천의 사건종류와 같다고 가정하지 않음 |
| `info.Reference_info.reference_rules` | 참조조문 메타데이터. 실제 법령 적용 여부의 정답 아님 |
| `sections[]` | `section_id/title/text/char_count`를 갖는 순서 있는 문서 구절 |
| `annotations[]` | `original_text/replacement_text/method/section_id/span/link_entity_id/rationale/rules_triggered` 등 비식별화 주석 |
| `annotations[].span[]` | 숫자 `start/end`. 위치 단위·끝점 포함 규약은 아직 미확인 |

`annotations`는 항소이유·판단 결과·심급 간 reasoning 변화의 gold label이 아니다. 개인정보 원문이 포함될 수 있는 `original_text`를 브라우저용 데이터로 내보내지 않는다. 원문·라벨 본문·마스킹을 재작성하지 않는다.

## 5. 정합성·불확실성

- 원천/라벨에 각각 공급자 식별값은 **18,879 distinct / 18,900행**이다. 중복된 식별값 그룹이 각각 21개라 `caseNoID` 단독 조인이 안전하지 않다.
- 같은 dataset/split/subset 안에서 공급자 ID+사건번호+법원+날짜로 대응 후보를 생성했다. 비교용 NFC·공백 제거와 `YYYYMMDD`/`YYYY-MM-DD` 표기만 정규화했다. 모든 원천 메타데이터는 별도 표현 행에 남긴다.
- 그 결과 원천↔라벨 **18,900개 대응 후보**가 있고 라벨 누락/다중 대응은 이번 조건에서 0개다. 이는 표현 간 대응이지 1심↔항소심 링크가 아니다. 모든 행의 법률 검증은 `unverified`다.
- 라벨 날짜에 연도 4287/4289/4291/4293인 행이 총 10개다. 시대·역법을 확인하기 전 서기 연도로 해석하거나 자동 환산하지 않는다. 기존 날짜 범위를 실제 연대 분포로 그대로 사용하지 않는다.
- 라벨 section은 161,186개다. 그중 `char_count`와 Python Unicode codepoint 길이가 다른 행은 40,695개다. 이 차이만으로 텍스트 오류라고 판정하지 않는다. 위치 단위를 확인하기 전 `char_count`로 span을 재계산하지 않는다.
- 원심 관련 표제 패턴이 있는 라벨 형사 문서는 1,924/2,700개다. 이는 정규식 표제 존재량이며 원심 문서가 실제로 연결되는 수나 항소심 수가 아니다.
- 원천의 사건종류 부재 685개와 판결유형 설명 부재 374개는 관측 결측으로 기록했다. 별도 법적 범주·심급을 생성하지 않았다.

## 6. 조사용 로컬 인덱스 계약

원본 ZIP을 불변 입력으로 두고 **SQLite 메타데이터 인덱스**를 생성했다. 본문 전체를 DB에 중복 적재하거나 브라우저에 붙이지 않았다. 내부 제목/문서 ID도 비공개 자료로 취급한다.

| 테이블 | grain / 주요 필드 |
|---|---|
| `archives` | ZIP 1개. dataset/split/role/subset·원래 상대경로·SHA-256·상태·entry/parsed 수 |
| `documents` | core ZIP의 JSON 표현 1개. `source_id`, archive ID, entry index+원래 경로, member hash, 공급자 ID·사건번호·날짜·분류, section/annotation 수, `unverified` |
| `sections` | 표현 내 section 1개. ordinal/ID/표제·텍스트 hash·codepoint/UTF-16 길이·공급 char_count. 본문은 없음 |
| `pairing_candidates` | 원천↔라벨 후보 edge 1개. 양끝 source_id·비교 근거·candidate/ambiguous |
| `issues` | entry별 오류/결측 관측. 오류 코드와 count, 본문 없음 |

`source_id`는 archive의 원래 경로+전체 hash에서 얻은 archive ID와 entry index로 만든 SHA-256이다. ZIP이 바뀌면 새 ID가 된다. 내장 공급자 ID도 보존하며 이를 사람/피고인 ID로 해석하지 않는다. `court_type` 열은 원천 판결유형 설명 또는 라벨 courtType을 그대로 담는 **표현별 필드**다. 공통 1/2/3심 정답으로 쓰지 않는다.

## 7. 실행과 사용

프로젝트 루트에서 Python 표준 라이브러리만 사용한다. 이번 입력 기준 Python 3.15.2에서 실행했다.

```bash
# 새 스냅샷 경로로 실행. 기존 결과는 덮어쓰지 않음.
python3 scripts/ingest/inventory.py scan --output data/private/inventory/new-snapshot
python3 scripts/ingest/verify_inventory.py data/private/inventory/new-snapshot

# SQL은 로컬 문서 ID/메타데이터를 출력하므로 공개 로그에 붙이지 않음.
sqlite3 -readonly data/private/inventory/2026-11-13-v4/catalog.sqlite < scripts/ingest/research.sql
```

원문이 필요하면 SQL로 찾은 `source_id`로 다음처럼 **비공개 파일**을 생성한다. source ID는 실제 카탈로그 값을 사용한다. archive hash와 member hash를 다시 확인한 후 ZIP의 원래 bytes를 쓴다. 새 파일만 생성하며 기존 출력은 덮어쓰지 않는다.

```bash
python3 scripts/ingest/inventory.py record \
  --catalog data/private/inventory/2026-11-13-v4/catalog.sqlite \
  --source-id SOURCE_ID_FROM_CATALOG \
  --output data/private/review/selected-record.json
```

이 JSON의 원문·개인정보를 외부 모델/공개 저장소로 전송할 권한은 이번에 확인하지 않았다. 공개 export는 구현하지 않았다. 코드 보정 중 생성한 임시 v1–v3는 폐기했으며 현재 사용 대상은 **v4 + verification.json**이다.

## 8. 다음 연구 단계의 열린 질문

1. 형사 라벨 분류와 원천 사건종류가 다른 경우 모집단/제외 사유를 어떤 근거로 기술할까? 원본 두 표현을 먼저 대조한다.
2. 원심 표제가 있는 문서 중 실제 1심 문서가 있는 것은 얼마나 될까? 표제 존재와 사건번호·법원·죄명의 대응을 분리해 검사한다.
3. 공급자 ID·공동피고인 별칭만으로 동일인을 확정할 수 있는가? 근거 없으면 정렬을 보류한다.
4. span과 char_count의 정의는 무엇인가? 공급 문서와 실제 문자열 대조 후에만 위치 계약을 동결한다.

이번 도구는 이 질문을 조사할 재현 가능한 기반이다. 법률 태스크와 시각적 설계의 사용자 답안을 대신 만들지 않았다.

**출처/AI 공개:** 로컬 `slides.pdf`와 manifest에 hash가 기록된 ZIP, 생성 SQL/검사 코드가 이번 수치의 근거다. Codex가 로컬 조사·인덱스·테스트·문서 초안을 작성했다. 데이터 품질 점검은 `data-analytics:analyze-data-quality` 스킬의 grain/중복/결측/조인 구분을 참고했다. 실제 법률 원문 검증과 공개 권리 판단은 미완료다.
